# Sales Performance Dashboard

<u>(README сгенерирован)</u> <br>
Dashboard аналитики продаж менеджеров для DJI-Market.ru: KPI со сравнением с предыдущим периодом, рейтинг менеджеров, динамика, разрез по категориям, лучшие товары и лента последних сделок.

**Стек:** ASP.NET Core 8 (Minimal API) · EF Core 8 + Dapper · PostgreSQL 16 · React + TypeScript + Vite · TanStack Query · Tailwind CSS 4 + shadcn/ui (Radix) · Recharts · Motion · Docker Compose

## Запуск

Нужен только Docker. Порты 3000, 8080 и 5433 должны быть свободны.

```bash
docker compose up --build
```

| Адрес | Назначение |
|---|---|
| http://localhost:3000 | Dashboard |
| http://localhost:8080/swagger | Swagger UI (контракты API) |
| localhost:5433 | PostgreSQL, БД / пользователь / пароль: `sales` / `sales` / `sales` |

Порядок старта обеспечивают healthcheck'и: `db` (healthy) → `backend` применяет миграции и seed → `backend` (healthy) → `frontend`. Когда страница открылась, данные уже на месте.

Пересоздать БД:

```bash
docker compose down -v
docker compose up --build
```

Учётные данные БД в `docker-compose.yml` относятся к локальной одноразовой базе.

## API

Все эндпоинты — `GET` в группе `/api/dashboard` с общими параметрами периода:

- `period`: `today` | `7d` | `30d` (по умолчанию) | `thisMonth` | `lastMonth` | `custom`
- `from`, `to`: `YYYY-MM-DD`, включительно. Обязательны только при `period=custom`, диапазон не длиннее 731 дня.

| Эндпоинт | Параметры | Ответ |
|---|---|---|
| `/summary` | — | KPI (значение, предыдущее, изменение), возвраты, отмены, лучший менеджер |
| `/managers` | `sortBy=grossProfit\|averageCheck` | рейтинг: место, изменение места, показатели, дельты |
| `/timeseries` | — | непрерывный ряд по дням, неделям или месяцам (≤62 дн / ≤190 дн / больше) |
| `/categories` | — | выручка, прибыль, маржа, доля по категориям |
| `/products/top` | `limit` 1–50, по умолчанию 5 | лучшие товары по валовой прибыли |
| `/sales/recent` | `limit` 1–50, по умолчанию 10 | последние сделки всех статусов с позициями |

Каждый ответ содержит `period` с фактическими датами текущего и предыдущего периода. Ошибки возвращаются в формате ProblemDetails: `400` с полем `errors` при ошибке валидации, `500` при ошибке сервера. `GET /api/health` проверяет доступность БД.

## Бизнес-правила

| Показатель | Правило |
|---|---|
| **Revenue** | Сумма `quantity × unit_price` по продажам со статусом `Paid` |
| **Cost** | Сумма `quantity × unit_cost` по `Paid`. Себестоимость фиксируется в позиции на момент продажи |
| **Gross Profit** | Revenue − Cost |
| **Margin** | Gross Profit / Revenue. При нулевой выручке — `null` |
| **Average Check** | Revenue / количество `Paid`-продаж. При нуле продаж — `null` |
| **Количество продаж** | Только `Paid` |
| **Cancelled** | Не входит ни в один финансовый показатель. Показывается отдельным счётчиком |
| **Refunded** | Полностью исключается из выручки, прибыли и количества. Относится к дате исходной продажи (отдельной даты возврата в модели нет). Показывается отдельно: количество и сумма |

**Период.** Полуинтервал `[from 00:00, to+1 00:00)` в часовом поясе бизнеса (`Europe/Moscow`, настройка `Business:TimeZone`). Продажа в 00:00:00 относится к новому дню, в 23:59:59 — к старому. «Сегодня» определяется по Москве, а не по часовому поясу браузера или UTC.

**Предыдущий период:**
- `today`, `7d`, `30d`, `custom` — интервал той же длины непосредственно перед текущим;
- `thisMonth` — то же число дней с начала прошлого месяца (1–29 сент ↔ 1–29 авг), с ограничением концом месяца (31 марта ↔ 28 февраля);
- `lastMonth` — позапрошлый месяц целиком.

**Изменение к предыдущему периоду:**
- для денег и количества — относительное, `(cur − prev) / |prev|`. Модуль в знаменателе нужен, чтобы рост из минуса в плюс не выглядел как падение;
- для маржи — разница в процентных пунктах;
- при `prev = 0` изменение равно `null`.

**Рейтинг:**
- Competition ranking: равные значения делят место (1-2-2-4). Порядок внутри равенства стабильный: по выручке, затем по имени.
- Менеджеры без продаж показываются без места и стоят в конце.
- Неактивные (уволенные) показываются, только если продавали в периоде.

## База данных

Таблицы: `managers`, `customers`, `categories`, `products`, `sales`, `sale_items`. Имена в snake_case (`EFCore.NamingConventions`).

- **Деньги** — `numeric(18,2)`, **время** — `timestamptz` в UTC. Npgsql не даёт записать не-UTC `DateTime`.
- **Статусы и сегменты** хранятся строками с check constraint. Check constraints также на количество, цены и итоги.
- **Итоги продажи денормализованы** (`sales.total_amount`, `total_cost`). KPI, рейтинг и динамика читают одну таблицу без JOIN на позиции. Согласованность обеспечивает единственная точка изменения `Sale.AddItem`, а продажа после создания меняет только статус.
- **`sale_items.unit_cost`** — снимок себестоимости на момент продажи: изменение закупочной цены не меняет маржу прошлых сделок.
- **Удаление:** `Restrict` для менеджера, клиента и товара (история не удаляется, для этого есть `is_active`), `Cascade` только для `sale_items → sales`.

**Индексы:**

| Индекс | Зачем |
|---|---|
| `sales(sold_at)` | Каждый запрос фильтрует по диапазону дат. «Последние продажи» — это `ORDER BY sold_at DESC LIMIT n` |
| `sales(manager_id, sold_at)` | Агрегаты по менеджеру за период. Ведущая колонка покрывает FK `manager_id` |
| `sales(customer_id)`, `sale_items(sale_id)`, `sale_items(product_id)`, `products(category_id)` | FK, используются в JOIN разрезов по товарам и категориям |
| `products(sku)` unique, `categories(name)` unique | Бизнес-ограничения |

Индекса по `status` намеренно нет: 3 значения, около 90% строк `Paid`, планировщик его не использует. На объёме seed (около 3 тыс. продаж) PostgreSQL чаще выбирает seq scan, и это правильно. Индексы рассчитаны на рост данных.

Миграции EF Core применяются при старте backend, этого требует запуск одной командой.

## Ключевые технические решения

- **Minimal API вместо контроллеров.** 6 однотипных read-only эндпоинтов одной фичи. Валидация периода кросс-полевая, атрибуты её не выражают. Ответы типизированы через `TypedResults`, поэтому Swagger видит схемы.
- **Где LINQ, где raw SQL.** LINQ для агрегатов (EF генерирует корректный SQL, проверено по логам: 1–3 запроса на эндпоинт, без N+1). Dapper + SQL для временного ряда: `generate_series` даёт непрерывную шкалу с нулями, `AT TIME ZONE` — группировку по дате бизнеса.
- **Один запрос на текущий и предыдущий период:** `GROUP BY (sold_at >= from, status)`.
- **Рейтинг.** Суммы считает PostgreSQL, в приложение приходит не больше 2 строк на менеджера, ранжирование на них выполняется в C#.
- **Время через `TimeProvider`.** «Сегодня» подменяется в тестах.
- **`CancellationToken` до SQL.** Устаревший запрос при быстрой смене периода отменяется и на стороне PostgreSQL.
- **Frontend: состояние периода и режима рейтинга в URL.**

## Seed-данные

Генератор `Data/Seed/SalesGenerator.cs` запускается автоматически при пустой БД.

**Объём:** 20 менеджеров в трёх командах, 75 клиентов в трёх сегментах, 6 категорий, 40 товаров, около 3 тыс. продаж за 12 месяцев.

**Реалистичность:**
- у менеджеров разная активность, склонность к скидкам и доля отмен;
- у каждого менеджера есть «постоянные» клиенты;
- корзина зависит от сегмента;
- сезонность: пик в ноябре–декабре, спад в январе, новогодние каникулы, выходные;
- рост бизнеса около 20% за год;
- около 1% позиций проданы ниже себестоимости.

**Воспроизводимость.** Фиксированный seed `Random`, все даты считаются от якорного дня. По умолчанию якорь — «сегодня» по Москве, поэтому dashboard всегда актуален, а при одном якоре данные идентичны. Чтобы зафиксировать данные в любой день, задайте `Seed:AnchorDate`, например в compose: `Seed__AnchorDate: "2026-09-30"`. «Сегодня» в сгенерированных данных почти пустое, чтобы не было продаж «из будущего».

**Edge cases для ручной проверки** (даты отсчитываются от дня seed):

| Сценарий | Где увидеть |
|---|---|
| Ничья: у Елены Поповой и Кирилла Васильева по одной одинаковой продаже | Произвольный период = вчера. Одно место в обоих режимах рейтинга |
| Граница суток | «Сегодня»: одна продажа в 00:00. Вчера: продажа в 23:59:59 |
| Очень крупная сделка (~28 млн ₽) | 100 дней назад, всплеск на графике |
| Крупный возврат | 60 дней назад: виден в ленте и счётчике возвратов, не в выручке |
| Продажа ниже себестоимости | 20 дней назад, отрицательная прибыль в ленте |
| Менеджер в отпуске | Ольга Воронцова, 55–40 дней назад |
| Уволенный менеджер | Роман Волков: нет в «30 дней», есть с пометкой в периоде 6+ месяцев |
| Новичок без продаж | Дмитрий Орлов, любой период |

## Тесты

```bash
dotnet test backend/SalesDashboard.sln   # нужен запущенный Docker
cd frontend && npm test
```

**Backend (xUnit).**
- Unit-тесты `PeriodResolver`: пресеты, часовой пояс, короткий февраль, гранулярность, валидация.
- Unit-тесты `Metrics` и ранжирования.
- Интеграционные тесты на реальном PostgreSQL (Testcontainers, отдельная БД на тест):
  - KPI и обработка статусов;
  - границы периода в полночь по Москве;
  - пустой период;
  - рейтинг: ничья, смена метрики, неактивные менеджеры;
  - временной ряд с группировкой по дате бизнеса.

**Frontend (Vitest + Testing Library + MSW).**
- Смена периода: URL → запрос → отрисовка.
- Переключение рейтинга.
- Состояния `Panel`: loading, error, empty, stale.
- Ошибка API и восстановление по «Повторить».

## Локальная разработка без Docker

```bash
docker compose up db                              # только PostgreSQL на порту 5433
dotnet run --project backend/SalesDashboard.Api   # Development: SQL EF пишется в консоль
cd frontend && npm install && npm run dev         # Vite проксирует /api на backend
```

Порт backend в `frontend/vite.config.ts` должен совпадать с портом из `launchSettings.json`.

Новая миграция:

```bash
dotnet ef migrations add <Name> --project backend/SalesDashboard.Api -o Data/Migrations
```
